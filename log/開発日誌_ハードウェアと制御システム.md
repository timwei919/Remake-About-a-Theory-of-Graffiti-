## 8/23 コントロールボックスを開けて信号を探す

- レーザーの制御信号(白線)を特定。ポンプはメイン基板に直結できる

中がどう繋がっているか見るために開けた。

```
緑基板(smartDIYs メイン制御、STM32)
  ├ 赤/黒:12V 電源 → 青基板
  └ 青/白:制御信号 → 青基板(レーザー定電流ドライバ)
                        └ LD+/LD− → レーザーヘッド
```

![](media/20260823_回路解析/20260823_制御ボックス内部_2.png)

青基板のクローズアップと、メイン基板のLASERコネクタ:

![](media/20260823_回路解析/20260823_青基板クローズアップ.png)
![](media/20260823_回路解析/20260823_LASERコネクタ.png)

テスターで測った結果:

| 計測点 | 結果 |
| --- | --- |
| レーザーヘッド出力端 LD+/LD− | 照射時 5.8V、停止後ゆっくり下がる |
| 白線(GND基準) | 0.2〜0.9V のあいだで動く |
| 青線(GND基準) | ずっと 0V |

最初はレーザーヘッドの出力端をそのままポンプのスイッチ信号に使おうとした。でも停止後の電圧がゆっくり下がる(ドライバ基板のコンデンサが放電している)ので使えない。そこで基板から上流へ辿っていって、緑基板と青基板のあいだの青白線が本当の制御信号だと分かった。

白線の0.2〜0.9Vという変な数字は、あとで考えるとPWMで、テスターは平均値しか出さないから。しかも計測したときレーザー出力を100%にしていなかった。

**結論:白線が制御信号。青基板は丸ごと飛ばせて、ポンプはメイン基板のLASERコネクタに直接ぶら下げられる。**

## 8/28〜29 Arduinoでポンプ制御 → レーザー信号で直接制御

- レーザー信号で直接ポンプを駆動できた

既存機の信号を流用する作業に入る前に、まずArduino Mega + MOSFETフォトカプラ絶縁基板でポンプを制御するテストをした。

Arduino Mega + MOSFETフォトカプラ絶縁基板(GYJ)でポンプを制御。シリアルでコマンドを打てば開閉できる。基板にフォトカプラ絶縁があるので、Arduinoと12VでGNDを共有しなくていい。動作を確認。

続いて、緑基板のLASERコネクタの白線・青線を**そのまま**MOSFET基板の信号入力につないでgcodeを走らせた——**レーザーが出力するはずの区間で、ポンプが本当に回った。** Arduinoを間に挟む必要もない。

出力100%ならポンプは安定して回る。30%を切ると水がほとんど出なくなる。出力が低いと振動する。PWMはポンプまで届いているが、デューティ比が低いとトルクが足りないということ。

### 循環時間について少し考える

一回の循環を10〜15分で回すのが目標なら、いまいちばんの問題は乾燥であって描画ではない。

描画は実は速い。速度4000で3mの経路なら3分もかからない。でも水が乾くまでの時間はそれよりずっと長いので、十分のうちほとんどが乾燥待ちに消える。つまり循環の長さを決めるのは、ポンプが水を送る速さと水が蒸発する速さの比ということになる。

扇風機がないとこの数字は話にならない(9/13に30分で乾かなかったのがその証拠)。**扇風機は周辺の部品ではなく、循環が成り立つかどうかの本体。** もともとPart 5に置いていたが、前倒しでテストして、蒸発効率の差を見ておくべき。

もうひとつ使っていない変数が**経路の長さ**。総水量 = 経路長 ×(流量/速度)なので、ずっと流量と速度をいじってきたが、図柄が疎になれば水量も減る。水量と蒸発の関係をちゃんとテストするには、藁科さんの機械学習の出力がそろそろ必要。

このあと水量の要求値もテストしないといけない。

### 自動化の設計方針

Max/MSPの自動化を考えはじめた。やることは四つ:

1. MaxがArduinoから湿度の値を読み、条件に達したら描画を開始する
2. MaxがArduino経由でソリッドステートリレーを制御し、扇風機を開閉する(描画中はOFF、描き終わったらON)
3. マウスの軌跡でSmartDIYs Creatorを操作する:「アイテムを追加」をクリック → ファイルを選ぶ → STARTをクリック
4. MaxがArduino経由でレーザー信号(白線)を拾い、一定時間水が出なければ描画終了と判定する


マウスの自動化は回り道のように見えるが、これはyang02のやり方に合っている——**技術の可視化**。議題A 4-3で整理したように、彼には「配線やpatchの画面をそのまま見せる」傾向があり、OISTのときは「注意深く追ってくと何がどうなってんのかわかる配線」が自分のこだわりだと書いている。

だとすれば、画面の上でカーソルが自分で動いて自分でボタンを押すという、そのこと自体が仕組みの露出になる。観客は機械が別の機械を操作しているのを見ることになる。隠された自動化ではなく、演じられた自動化。

→ なので自動化の方法は原作に倣うべきで、しかも**カーソルの動きは見えるべき**。これが道具の選択に関わってくる(下)。

#### カーソルはどう動くべきか
はじめは自分の操作した軌跡を録って再生する案を考えていた(人の手つきを一度録って、機械が永遠に繰り返す。概念としてはとても合っている)。ところが**記録映像をもう一度見ると、カーソルの動きが非常に直線的で、録った人間の軌跡には見えない**。二点間を線形補間したプログラムの動きだった。

だとすると原作はMaxの中で直接カーソルを制御していたのだろう。もっとも可能性が高いのは **aka.mouse** 。`[line]`で二点間を補間すれば、出てくる動きは完全な直線になる。

**ただしaka.mouseはサポートが終了していて**、いまのMax / macOSでは動かない。そこで **11clicks** を使うことにした。

![](media/20260916_ソフトとノズル/11clicks_help.png)

11clicksも既定では一瞬で飛ぶので、補間は自分でやる必要がある——経路を何十かに切って、一段ずつ `m:x,y` + `w:ms`。こうすれば動きは直線で滑らかになり、原作の映像で見たものと同じになる。移動時間は900msくらいに設定すると、人が操作しているように見える。

#### 描画終了はどう判定するか

**Arduinoにもレーザー信号(白線)を読ませる** → 信号が連続してN秒静まったら描き終わり。

これを選ぶ。白線はもともとあるので、ピンを一本増やすだけ。これでArduino一個が、湿度を読む・レーザー信号を読む・扇風機を制御する、の三つを同時にやることになる。ポンプは相変わらずレーザー信号が直接駆動して、Arduinoは通らない。

信号の状態の整理:

```
1. 湿度 ≥ 乾燥閾値 + 描画中でない → 乾燥待ち(扇風機 ON)
2. 湿度 < 乾燥閾値 + 描画中でない → マウスの軌跡を再生 + 扇風機 OFF
3. (描画中)レーザー信号が N 秒静まる → 終了
4. 1 に戻る
```

閾値にはヒステリシス帯が必要。でないと読み値が境目で揺れたときに扇風機が開閉を繰り返してしまう。

### ノズルのところの構成が分かった

水が出る最後の部分がやっと分かった。**透明なアクリルの硬い管の中に、チューブが少し蛇行しているのが見える。**

*(原作の記録映像からのキャプチャ。著作権が作家・撮影者に帰属するため、本リポジトリには含めない)*
*(原作の記録映像からのキャプチャ。著作権が作家・撮影者に帰属するため、本リポジトリには含めない)*

構成はこうなる:

```
シリコンチューブ(推測 内径3×外径5)
   ↓ 通す
透明アクリルの硬い管(垂直の固定支持として)
   ↓ 下端から少しだけ出る
シリコンチューブ + 異径コネクター(ノズル)
```

これで9/9に残った疑問が解けた。上の部分がチューブなのか硬い管なのか分からなかったが、答えは**両方**だった。チューブが中にあるから半透明に見え、アクリルが外にあるから真っ直ぐに見える。

#### 買うもの

アクリルの硬い管、内径6 / 外径8。シリコンチューブの外径5を内径6に通すと1mmの隙間ができるので、通せるし蛇行する余地も残る。

### Arduino と Max/MSP のコードを書いた

#### Arduino:`arduino/GraffitiIO/GraffitiIO.ino`

センシングと扇風機を担当して、ポンプには関わらない(ポンプはレーザー信号がMOSFET基板経由で直接駆動する)。

やることは三つ。水分センサーを読む、レーザー信号を監視して静寂の時間を出す、コマンドに従ってSSRで扇風機を開閉する。100msごとに `st <hum> <laser> <silent> <fan>` を一行Maxへ送り、受け取るコマンドは `f1` / `f0` だけ。

配線:A0 水分センサー / D4 センサーVCC(読むときだけ通電) / D2 レーザー信号(白線) / D8 SSR。

閾値の判断とステートマシンはここには置かず、Maxに残す。こうすれば閾値を変えるのに書き込み直さなくていい。

#### Max/MSP:`max/GraffitiControl.maxpat`

総指揮。六つのブロックに分かれている。

- **⓪ 状態欄** モード、状態、湿度、給水、静寂の秒数、扇風機、受信
- **① 通信** Arduinoからのシリアルを受けて四つの値に分ける
- **② 判定** 乾燥の閾値と静寂の閾値。どちらもその場で変えられる
- **③ 状態遷移** 乾燥待ち ⇄ 描画中。GUARD(描画の直後は静寂判定を止める)と自動/手動モードの切り替えを含む
- **④ 扇風機** Arduinoへ `f1` / `f0` を送る
- **⑤ マウス操作** 六手順の表:移動 → 左クリック → 待つ。ウェブ版の制御ソフトを操作する
- **⑥ 手動操作** 自動判定を飛ばすボタン

あえて純粋なMaxオブジェクトで書いて `[js]` には包まなかった。このpatchは観客に見せるものなので、ブラックボックス化すると技術の可視化という層が消えてしまう。

#### Arduino ↔ Max の実機テスト

- Maxが Arduino から湿度の値を読む:**成功**
- Maxが Arduino 経由でソリッドステートリレーを制御する:**成功**
- レーザー信号の読み取り:**まだ**。Type-Aのポートが足りない(プロッターもArduinoもひとつずつ占有する)。明日、口数の多いType-C to Aのアダプターを持ってきてから繋ぐ。

#### 二回目でなぜ厚くしたのか(仮説)

水はブロックの上で蒸発するだけでなく、ブロックの中へも吸われていく。厚いブロックは吸水の容量が大きいので、連続運転したときに飽和するまでが長い。

この仮説が当たっているなら、自分にとって重要な注意になる。**乾燥時間は運転時間が伸びるにつれて長くなる可能性がある。** いま測っているのはどれも乾いたブロックの一回目か二回目で、単発のデータ。確かめるには数時間連続で回して、乾燥時間が伸びるかどうかを見ればいい。

#### 決めること

本番でどちらを使うか。いまのところ厚いほうに傾いている(長時間の運転に対応するため)が、まず会場の荷重と搬入の条件を確認する必要がある。薄いほうしか使えないなら、「連続運転で乾燥時間が伸びる」ことを既知の制約として循環を設計する。
